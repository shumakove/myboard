# Workflow: разработка и независимое тестирование

Документ фиксирует, как два агента — **DEV** (разработчик) и **QA** (тестировщик) — передают друг другу задачи из [PLAN.md](PLAN.md). Поведение продукта берётся только из [REQUIREMENTS.md](REQUIREMENTS.md), устройство — из [ARCHITECTURE.md](ARCHITECTURE.md). Ни один агент эти два документа не меняет: изменения в них вносит только владелец проекта (человек).

## 1. Роли и границы

| | DEV | QA |
| --- | --- | --- |
| Пишет | `apps/web`, `apps/api`, `deploy/`, модульные тесты рядом с кодом (`apps/api/tests/test_<module>.py`, `*.test.ts(x)`), UML-схемы в `uml/`, карточки `docs/tasks/`, `docs/decisions.md` | Приёмочные тесты в `acceptance/`, отчёты `docs/qa/`, баги `docs/bugs/` |
| Не трогает | `acceptance/`, `docs/qa/`, `docs/bugs/` | Код продукта, модульные тесты DEV, `deploy/`, `uml/`, `docs/tasks/`, `docs/decisions.md` (только читает) |
| Отвечает за | Реализацию требования, зелёные модульные тесты и актуальность `uml/` | Вердикт PASS / FAIL по каждому ID требования |
| Меняет статус | `TODO → IN_DEV → READY_FOR_QA`, `REJECTED → IN_DEV`, `ACCEPTED → DONE` | `READY_FOR_QA → IN_QA → ACCEPTED` или `→ REJECTED`; свои задачи `Q*` — от `TODO` до `DONE` |

Модульные тесты DEV проверяют модуль изнутри (правила `.cursor/rules/tests.mdc`). Приёмочные тесты QA проверяют систему снаружи — только через публичные интерфейсы: HTTP, WebSocket, браузер. QA не импортирует код из `apps/` и не опирается на внутренние функции.

## 2. Правила разработки

Для DEV обязательны правила из `.cursor/rules/`:

- `development.mdc`:
  - код пишется по best practice языка (Python — PEP 8 и типизация, TypeScript — строгий режим);
  - комментарии краткие и по делу;
  - clean code и single responsibility: одна функция, компонент или модуль отвечает за одно;
  - без переусложнения: самое простое решение, закрывающее требование;
  - код читабельный;
  - при реализации функционала обновляется единая папка `uml/` (порядок — раздел 4.4).
- `tests.mdc`: модуль не готов без тестов его наблюдаемого поведения; тесты пишутся в том же изменении и прогоняются перед передачей.

Поведение продукта берётся из `REQUIREMENTS.md`, устройство — из `ARCHITECTURE.md` (см. `CLAUDE.md`). За соблюдение правил разработки отвечает DEV; QA качество кода не оценивает, а проверяет требования и наблюдаемые решения архитектуры.

## 3. Артефакты

```text
PLAN.md                         задачи и их статусы (колонка «Статус» в сводной таблице)
docs/tasks/<TASK-ID>.md         карточка DEV: handoff, исправления, UML
docs/qa/reports/<TASK-ID>.md    отчёт QA: сценарии (фиксируются до чтения handoff), вердикты
docs/bugs/BUG-<NNN>.md          дефект, найденный QA
docs/questions.md               неясности в требованиях, на которые отвечает владелец
docs/decisions.md               технические решения DEV: выбранные библиотеки и почему
docs/qa/traceability.md         матрица «ID требования → приёмочный тест → вердикт»
acceptance/api/test_<area>.py   pytest + httpx + websockets против запущенного стека
acceptance/e2e/<area>.spec.ts   Playwright: профили desktop и mobile (ширина телефона, touch)
uml/                            UML-схемы принятой реализации (правила — uml/README.md)
.claude/agents/developer.md     описание агента DEV для Claude Code
.claude/agents/tester.md        описание агента QA для Claude Code
```

Рабочие копии и стеки — агенты работают параллельно и друг другу не мешают:

| | DEV | QA |
| --- | --- | --- |
| git worktree | `../myboard-dev` | `../myboard-qa` |
| Проект Compose | `myboard-dev` | `myboard-qa` |
| Порт Caddy | `8080` (`PUBLIC_BASE_URL=http://<IP>:8080`) | `80` (`PUBLIC_BASE_URL=http://<IP>`) |

Основная копия репозитория используется только для коммитов прямо в `main`: статусы `PLAN.md`, `docs/questions.md`, `docs/qa/` и `docs/bugs/`. Эти файлы общие, поэтому живут в `main`, а не в ветках: так вопрос или отклонённый отчёт виден второму агенту сразу. Код, тесты, карточки `docs/tasks/`, `docs/decisions.md` и `uml/` идут через ветки.

Ветки git:

- `dev/<TASK-ID>` — код и модульные тесты DEV.
- `qa/<TASK-ID>` — приёмочные тесты QA (`acceptance/`), ответвляется от `main`, а не от ветки DEV.
- `uml/<TASK-ID>` — обновление схем DEV после приёмки, ответвляется от `main` после слияния задачи.
- Код попадает в `main` только после вердикта PASS: QA сливает `dev/<TASK-ID>` и `qa/<TASK-ID>` и ставит `ACCEPTED`. Затем DEV сливает `uml/<TASK-ID>` и ставит `DONE`.
- Ветки и `main` отправляются в `origin` сразу после коммита. `push --force` и переписывание истории `main` запрещены обоим агентам.

## 4. Жизненный цикл задачи

```mermaid
stateDiagram-v2
  [*] --> TODO
  TODO --> IN_DEV: DEV берёт задачу
  IN_DEV --> READY_FOR_QA: handoff готов, модульные тесты зелёные
  READY_FOR_QA --> IN_QA: QA берёт задачу
  IN_QA --> ACCEPTED: все ID требований PASS, регрессия зелёная, слияние в main
  ACCEPTED --> DONE: DEV обновил uml/ по принятой реализации
  IN_QA --> REJECTED: есть FAIL или BLOCKER
  REJECTED --> IN_DEV: DEV исправляет баги
  IN_DEV --> BLOCKED: вопрос DEV к владельцу
  BLOCKED --> IN_DEV: владелец ответил на вопрос DEV
  IN_QA --> BLOCKED: неясное требование
  BLOCKED --> IN_QA: владелец ответил в docs/questions.md
  DONE --> [*]
```

### 4.1. DEV: от TODO до READY_FOR_QA

Подробный регламент агента — `.claude/agents/developer.md`. За один запуск DEV выполняет одну единицу работы по приоритету из раздела 7 и завершает запуск отчётом.

1. Берёт первую задачу в `TODO`, у которой все зависимости в `ACCEPTED` или `DONE`. Ставит `IN_DEV` в `PLAN.md`.
2. Создаёт ветку `dev/<TASK-ID>` от `main` в worktree `../myboard-dev`.
3. Реализует пункты блока «Разработка» задачи. В коде указывает ID закрываемых требований. Библиотеки, не названные в `ARCHITECTURE.md`, выбирает сам и записывает решение в `docs/decisions.md`.
4. Пишет модульные тесты в том же изменении и прогоняет тесты затронутых модулей.
5. Прогоняет проверки качества: Python — `ruff check`, `ruff format --check`, `mypy --strict`; TypeScript — `tsc --noEmit`, ESLint, Prettier.
6. Поднимает стек `myboard-dev` с нуля (пустые тома) и проходит сценарии блока «Тестирование»: API — `curl`, интерфейс — через Claude in Chrome. Это smoke-проверка, а не приёмка.
7. Если неясность в требовании или архитектуре меняет реализацию — вопрос в `docs/questions.md`, статус `BLOCKED`, запуск завершается.
8. Заполняет раздел «Handoff» в `docs/tasks/<TASK-ID>.md` (шаблон ниже), отправляет ветку в `origin` и ставит `READY_FOR_QA`.

**Definition of Ready for QA** — без этого QA возвращает задачу, не начиная проверку:

- ветка собирается, стек поднимается командой из handoff на пустых томах;
- модульные тесты затронутых модулей зелёные, вывод приложен;
- линтеры, форматтеры и проверка типов зелёные;
- каждое требование из задачи перечислено в handoff с пометкой «реализовано» или «не реализовано, причина»;
- указаны новые маршруты, эндпоинты, сообщения WebSocket и способ подготовить данные (например, как создать пользователя).

### 4.2. QA: независимая проверка

Порядок важен: сценарии проектируются **до** чтения handoff и кода, чтобы реализация не подсказала, что проверять.

1. Берёт задачу `READY_FOR_QA`, ставит `IN_QA`.
Подробный регламент агента — `.claude/agents/tester.md`. За один запуск QA выполняет одну единицу работы и завершает запуск отчётом.

2. **Проектирование от требований и фиксация.** Читает только формулировки требований из `REQUIREMENTS.md`, контекст из `ARCHITECTURE.md` и блок «Тестирование» задачи. Для каждого ID выписывает в `docs/qa/reports/<TASK-ID>.md` сценарии: позитивный, негативный, граничный. Отдельно — роль: пользователь досок, участник по ссылке, администратор, посторонний без доступа. Добавляет проверки наблюдаемых решений архитектуры, относящихся к задаче: маршруты, сообщения WebSocket, формат ZIP, заголовки фреймов, флаги cookie, отсутствие `localhost`. **Сценарии коммитятся в `main` и отправляются в `origin` до чтения handoff и кода** — коммит доказывает, что реализация не подсказала проверки.
3. **Подготовка окружения.** Чистый checkout `dev/<TASK-ID>` в worktree `../myboard-qa`, `docker compose -p myboard-qa down -v && docker compose -p myboard-qa up --build`, переменные из `deploy/compose/.env.example`. Ничего из локального состояния DEV не переиспользуется.
4. **Чтение handoff.** Только теперь — чтобы узнать маршруты и способ подготовки данных. Если не выполнен Definition of Ready for QA — `REJECTED` с перечнем недостающего, без проверки. Если handoff расходится с требованием, прав текст требования.
5. **Автоматизация.** Пишет приёмочные тесты в ветке `qa/<TASK-ID>`: имя теста содержит ID требования (`test_shr06_reset_revokes_old_link`, `test('CVS-12 shift constrains drag to axis')`). Сенсорные жесты, ладонь и стилус проверяются эмуляцией в Playwright (`hasTouch`, `pointerType`). Где автоматизация неоправданно дорога (например, воспроизведение видео), QA проводит ручную проверку через Claude in Chrome и фиксирует шаги и результат в отчёте.
6. **Прогон.** Новые тесты + весь набор `acceptance/` (регрессия) + модульные тесты DEV (проверка, что они действительно зелёные).
7. **Сверка модульных тестов DEV.** QA читает их и отмечает в отчёте требования, поведение которых модульные тесты не покрывают. Это замечание, а не FAIL.
8. **Вердикт** по каждому ID: `PASS`, `FAIL` (с BUG-номером) или `BLOCKED` (с вопросом в `docs/questions.md`). Нарушение наблюдаемого решения архитектуры — тоже баг. Обновляет `docs/qa/traceability.md`.
9. **Итог.**
   - Все ID `PASS`, регрессия зелёная, открыты только minor-баги → QA сливает `dev/<TASK-ID>` и `qa/<TASK-ID>` в `main`, прогоняет регрессию на `main`, ставит `ACCEPTED`. Minor-баги остаются открытыми и перечислены в отчёте.
   - Хотя бы один `FAIL` с blocker или major → `REJECTED`, баги заведены.
   - Нет `FAIL`, но есть `BLOCKED` → `BLOCKED` до ответа владельца.
   - Конфликт слияния или красная регрессия на `main` → QA не правит код: отменяет своё неотправленное слияние, заводит баг, ставит `REJECTED`.

### 4.3. Возврат и повторная проверка

- DEV исправляет баги в той же ветке `dev/<TASK-ID>`, для каждого бага добавляет модульный тест, воспроизводящий дефект, и дописывает в handoff раздел «Исправления» со ссылками на BUG.
- QA при повторной проверке прогоняет **все** сценарии задачи и регрессию, а не только исправленные.
- Приёмочный тест, упавший из-за бага, остаётся в наборе навсегда.
- Если DEV считает, что приёмочный тест проверяет не то, что написано в требовании, он задаёт вопрос в `docs/questions.md` со ссылкой на баг. Спор решает владелец; ни один агент не правит чужие файлы, чтобы «пройти».
- Исправленный и перепроверенный баг QA отмечает в его файле: «Исправлен в <sha>, проверено».

### 4.4. DEV: от ACCEPTED до DONE — обновление UML

Схемы в `uml/` описывают только принятую и протестированную реализацию, поэтому обновляются после вердикта PASS, а не во время разработки: код, вернувшийся на доработку, в схемы не попадает.

1. DEV создаёт ветку `uml/<TASK-ID>` от `main`, в котором уже лежит принятый код.
2. Обновляет схемы по фактическому коду из `main`, а не по плану задачи и не по `ARCHITECTURE.md`: какие диаграммы затрагивает задача — по таблице в `uml/README.md`.
3. Если реализация разошлась с `ARCHITECTURE.md`, схема отражает код, а расхождение DEV записывает вопросом в `docs/questions.md` для владельца.
4. В ветке меняется только `uml/`; код продукта и тесты не трогаются. Нужна правка кода — это новая задача или баг.
5. DEV дописывает в карточку раздел «UML» со списком изменённых схем, сливает ветку в `main` и ставит `DONE`.

## 5. Правила независимости

- QA не принимает объяснения из handoff вместо проверки поведения: «так задумано» не довод, если требование говорит иное.
- QA не смотрит модульные тесты DEV на шаге проектирования сценариев.
- QA проверяет каждую задачу минимум в двух ролях, если требование касается доступа (владелец и участник по ссылке; для закрытых ресурсов — ещё и посторонний).
- Для совместной работы (COL-*, SHR-04, realtime) QA открывает минимум два независимых клиента (два контекста браузера или два WebSocket-клиента) и проверяет, что правка одного видна другому.
- Для мобильных требований (MOB-*) — профиль Playwright с шириной телефона и эмуляцией touch и стилуса. Проверки на реальном устройстве в процесс не входят.
- Адреса в тестах берутся из `PUBLIC_BASE_URL`, `localhost` в приёмочных тестах не вписывается.
- Если требование допускает два толкования, QA не выбирает удобное: задача `BLOCKED`, вопрос в `docs/questions.md`.

```markdown

Коммит сценариев: <sha коммита в main до чтения handoff>

## Сценарии

| Требование | Роль | Сценарий | Тип (авто / ручной) |
| --- | --- | --- | --- |
| SHR-06 | участник по ссылке | После сброса старый токен и cookie не дают доступа | авто |

```

Каждая повторная проверка добавляет новый раздел «Проверка N», прежние не переписываются.

### 6.3. Баг `docs/bugs/BUG-<NNN>.md`

```markdown
# BUG-<NNN> · <кратко>

Задача: <TASK-ID>   Требование: <ID>   Серьёзность: blocker | major | minor
Коммит: <sha>   Окружение: desktop | mobile профиль Playwright | Claude in Chrome

Шаги:
1. …
Ожидалось (цитата требования): …
Фактически: …
Доказательство: <тест, лог, скриншот>
```

Серьёзность: **blocker** — требование не выполняется или нарушен доступ/безопасность; **major** — требование выполняется частично; **minor** — отклонение, не мешающее требованию (вёрстка, текст). Задача с открытым blocker или major не получает `ACCEPTED`. Minor не мешает приёмке: баг остаётся открытым в `docs/bugs/`, упоминается в отчёте, и владелец решает, когда его исправлять.

## 7. Синхронизация агентов

- Единственный источник статуса — сводная таблица в `PLAN.md`. Агент меняет статус отдельным коммитом в `main` с сообщением `Статус <TASK-ID>: <старый> → <новый>`.
- Зависимость задачи считается выполненной, когда она в `ACCEPTED` или `DONE`: код уже в `main`.
- DEV может вести следующую задачу, пока предыдущая в `IN_QA`, если она не зависит от непроверенной. Приоритет DEV: исправление `REJECTED`, затем обновление UML задач в `ACCEPTED`, затем `BLOCKED` с отвеченным вопросом DEV, затем новая задача.
- Приоритет QA: `BLOCKED` с отвеченным вопросом QA, затем `READY_FOR_QA` (повторные проверки первыми), затем свои задачи `Q*`, затем закрытие фазы, затем заблаговременные сценарии для задач в `IN_DEV` — только по требованиям, без доступа к ветке DEV.
- Закрытие фазы: когда все задачи фазы в `DONE` (включая UML), QA делает полный регрессионный прогон на `main` в профилях desktop и mobile и отмечает фазу закрытой в `PLAN.md`.
