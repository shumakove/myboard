Требования: основа COL-07, COL-08 (сами требования закрывает T8.2); проверка «присутствие не попадает в снимки», отложенная QA из T4.2
Ветки: dev/T4.3, qa/T4.3

## Handoff (DEV)

Коммит: см. последний коммит ветки `dev/T4.3`
Запуск (из корня репозитория):

```sh
docker compose --project-directory deploy/compose -p <проект> down -v
docker compose --project-directory deploy/compose -p <проект> up --build
```

Переменные — из `deploy/compose/.env.example`. Новая **необязательная** переменная `SNAPSHOT_INTERVAL_SECONDS` (по умолчанию 300): период фонового снимка открытой доски. Для проверки удобно поднять стек с `SNAPSHOT_INTERVAL_SECONDS=5` (в `.env` или в окружении команды `up`). Новая миграция `0007` (таблицы `board_snapshots`, `board_events`). Новых зависимостей, HTTP-эндпоинтов, схем OpenAPI и типов сообщений WebSocket нет.

Подготовка данных (как в T4.1/T4.2):
1. Администратор: `POST /api/admin/login`, `POST /api/admin/users {"name","email","password"}`.
2. Владелец: `POST /api/login` → cookie `myboard_session`; доска `POST /api/boards {"title"}`.
3. Ссылка: `GET /api/boards/{id}/share` → `token`; участник: `POST /api/share/{token}/join {"name"}` → cookie `myboard_board_{id без дефисов}`.
4. Канал: владелец — `ws://<host>/api/ws?board={id}`, участник — `ws://<host>/api/ws?token={token}` (протокол `sync` — T4.1).
5. Состояние в БД: `docker compose -p <проект> --project-directory deploy/compose exec postgres psql -U myboard -d myboard -c "select count(*) from board_updates where board_id='<id>'"` (аналогично `board_snapshots`, `board_events`).

Когда сжимается журнал (снимок в `board_snapshots` + удаление вошедших строк `board_updates` одной транзакцией):
- раз в `SNAPSHOT_INTERVAL_SECONDS` для открытой доски, если с прошлого снимка были правки;
- когда с доски уходит последнее соединение (если были правки);
- при остановке процесса `api` (`docker compose restart api`, `stop`).
Доска без новых правок новых снимков не получает.

Удаление объекта (формат документа): одной транзакцией Yjs ключ уходит из `objects`, а в `trash[id]` появляется `Y.Map { object: <копия объекта>, deletedAt: "<ISO 8601>", deletedBy: "<имя>" }`. Клиентская функция — `moveToTrash(board, ids, deletedBy)` в `apps/web/src/realtime/boardDocument.ts`; кнопок удаления в интерфейсе ещё нет (объекты — T5.2/T5.3), проверка — WebSocket-клиентом. Сервер на каждое принятое обновление, добавившее ключи в `trash`, пишет `board_events`: `actor_name` = имя из сессии соединения (не `deletedBy`), `event_type = "objects_deleted"`, `payload = {"object_ids": ["<id>", …]}`.

Известные ограничения:
- Снимки не удаляются (так в архитектуре: «остаются, пока доска не удалена»); окончательное удаление доски с журналом — вне задачи.
- Запись ленты пишется только для удаления (`objects_deleted`); прочие типы действий и восстановление — T8.2.
- Замечание QA на будущее (T5/T6): текст объектов хранить в `Y.Text` — `moveToTrash` уже копирует вложенные общие типы (`clone()`), тест — с `Y.Text`.
