# T0.2 · QA-отчёт

Требования: — (инфраструктурная задача; проверяются блок «Тестирование» T0.2 в `PLAN.md` и наблюдаемые решения ARCHITECTURE.md, разделы 1, 3, 5, 7, 11)
Коммит сценариев: <заполняется после коммита>

Сценарии составлены только по `PLAN.md` (блоки «Разработка» и «Тестирование» T0.2), `ARCHITECTURE.md` и `CLAUDE.md`, до чтения handoff и кода. Идентификаторы проверок: `ARCH-CFG-*` (обязательные переменные), `ARCH-MIG-*` (Alembic, миграции до приёма трафика), `ARCH-OAS-*` (публикация OpenAPI), `ARCH-PROC-*` (процесс API), `ARCH-DEVTOOL-*` (инструменты и модули, проверяемые запуском в ветке DEV).

Роли: в T0.2 ещё нет учётных записей, досок и ссылок; все HTTP-проверки выполняются как «посторонний» (анонимный клиент без cookie) через Caddy по `PUBLIC_BASE_URL`. Роль «оператор» — тот, кто запускает процесс (переменные окружения, логи). Проверки прав пользователя досок, участника по ссылке и администратора появятся в T1.1–T3.1.

## Сценарии

| Проверка | Роль | Сценарий | Тип (авто / ручной) |
| --- | --- | --- | --- |
| ARCH-CFG-01 | оператор | Негативный: процесс API, запущенный без переменной (переменная отсутствует в окружении), для **каждой** из `PUBLIC_BASE_URL`, `SECRET_KEY`, `DATABASE_URL`, `MEDIA_ROOT`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `MAX_UPLOAD_BYTES` по очереди завершается с ненулевым кодом, и вывод содержит имя отсутствующей переменной | авто (pytest, `docker run` образа `api`) |
| ARCH-CFG-02 | оператор | Позитивный: с полным набором переменных из `.env.example` процесс стартует и отвечает через Caddy (`/api/openapi.json` 200) | авто |
| ARCH-CFG-03 | оператор | Граничный: отсутствуют сразу две переменные — процесс не стартует, вывод называет хотя бы одну из них (желательно обе) | авто |
| ARCH-CFG-04 | оператор | Граничный: переменная задана пустой строкой (`PUBLIC_BASE_URL=`, `SECRET_KEY=` и т.д.) — процесс не стартует с именем переменной в выводе. Если пустое значение принимается — вопрос владельцу, а не FAIL (в требовании сказано «без переменной») | авто (информативно) |
| ARCH-CFG-05 | оператор | Негативный: `MAX_UPLOAD_BYTES` не целое число (`abc`) — процесс не стартует, вывод называет `MAX_UPLOAD_BYTES` | авто |
| ARCH-CFG-06 | оператор | Безопасность: сообщение об отсутствующей переменной не печатает значения секретов (`SECRET_KEY`, `ADMIN_PASSWORD`, пароль из `DATABASE_URL`) | авто |
| ARCH-MIG-01 | оператор / посторонний | Позитивный: после `down -v && up --build` (пустая база) в PostgreSQL есть таблица `alembic_version` с одной ревизией, и первый же HTTP-запрос к API через Caddy обслуживается (нет 5xx из-за отсутствующих таблиц) | авто (pytest + `docker compose exec postgres psql`) |
| ARCH-MIG-02 | оператор | Позитивный: миграции применяются **до приёма трафика** — в логе `api` применение миграций (или их выполнение отдельным шагом до старта сервера) идёт раньше строки о начале приёма соединений; сервер не слушает порт, пока миграции не завершены | ручной (логи `docker compose logs api`) + авто (порядок строк лога) |
| ARCH-MIG-03 | оператор | Граничный: перезапуск `api` на уже мигрированной базе проходит без ошибок, ревизия в `alembic_version` не меняется, данных повторно не создаётся | авто |
| ARCH-MIG-04 | оператор | Негативный: база недоступна (`DATABASE_URL` на несуществующий хост) — процесс не начинает принимать трафик (завершается с ошибкой или не проходит готовность), а не обслуживает запросы без схемы | авто |
| ARCH-MIG-05 | оператор | Миграции только вперёд: цепочка ревизий линейна (одна голова); путь отката не является частью процедуры запуска (запуск делает только `upgrade`) | ручной (после шага 4: `alembic heads`, `alembic history` в контейнере) |
| ARCH-MIG-06 | оператор | Таблицы из раздела 7 создаются «по мере надобности»: в T0.2 наличие конкретных таблиц не требуется; если таблицы есть — их имена совпадают с разделом 7 архитектуры | ручной (`\dt`) |
| ARCH-OAS-01 | посторонний | Позитивный: `GET {PUBLIC_BASE_URL}/api/openapi.json` → 200, `Content-Type: application/json`, тело — документ OpenAPI 3.x (`openapi`, `info.title`, `info.version`, `paths`) | авто |
| ARCH-OAS-02 | посторонний | Позитивный: все пути в `paths` начинаются с `/api` (клиент ходит на `/api` того же происхождения, раздел 10) — либо схема задаёт `servers` с `/api` | авто |
| ARCH-OAS-03 | посторонний | Граничный: `HEAD`/повторный `GET` и запрос с query (`/api/openapi.json?x=1`) также отдают схему; ответ не HTML интерфейса | авто |
| ARCH-OAS-04 | посторонний | Негативный: несуществующий путь `/api/<случайный>` → 404 JSON от FastAPI (регрессия ARCH-PROXY-02 уже на настоящем API) | авто |
| ARCH-OAS-05 | посторонний | В схеме нет ссылок на `localhost`/`127.0.0.1` (в `servers` и где-либо ещё) | авто |
| ARCH-PROC-01 | оператор | Сервер — Python 3.12 (`python --version` в контейнере `api`) | ручной |
| ARCH-PROC-02 | оператор | Один процесс приложения: в контейнере `api` работает один воркер приложения (нет нескольких воркеров uvicorn/gunicorn) | ручной (`ps` в контейнере) |
| ARCH-PROC-03 | посторонний | Регрессия T0.1: WebSocket `/api/ws` через Caddy доходит до настоящего API (101 или отказ, сформированный API), запрет фрейма на ответах API сохранён | авто (набор T0.1) |
| ARCH-DEVTOOL-01 | оператор | В ветке DEV `apps/api` управляется `uv` (`pyproject.toml`, lock-файл); `uv sync` проходит на чистой копии | ручной (запуск) |
| ARCH-DEVTOOL-02 | оператор | `uv run ruff check`, `uv run ruff format --check`, `uv run mypy --strict` в `apps/api` зелёные | ручной (запуск) |
| ARCH-DEVTOOL-03 | оператор | `uv run pytest` в `apps/api` зелёный; есть фикстуры тестовой БД и клиента (наличие проверяется запуском, качество кода не оценивается) | ручной (запуск) |
| ARCH-DEVTOOL-04 | оператор | Серверные модули `identity`, `library`, `sharing`, `realtime`, `history`, `media`, `backup` присутствуют в `apps/api` как отдельные модули с роутерами, подключёнными к приложению | ручной (структура каталогов, после шага 4) |
