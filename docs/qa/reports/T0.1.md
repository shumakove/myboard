# T0.1 · QA-отчёт

Требования: — (инфраструктурная задача; проверяются наблюдаемые решения ARCHITECTURE.md, разделы 2, 4, 5 «Участник по ссылке», 10, 11, 12)
Коммит сценариев: см. коммит «T0.1: Зафиксировать приёмочные сценарии» в `main` (до чтения handoff)

Сценарии составлены только по `PLAN.md` (блок «Тестирование» T0.1), `ARCHITECTURE.md` и `CLAUDE.md`, до чтения handoff и кода. Идентификаторы проверок: `ARCH-STACK-*` (сервисы и тома), `ARCH-NET-*` (порт и адрес в LAN), `ARCH-PROXY-*` (прокси `/api`, `/api/ws`), `ARCH-FRAME-*` (запрет фрейма, EMB-04 в части заголовков).

Роли: в T0.1 ещё нет учётных записей и досок, поэтому все проверки выполняются как «посторонний» (анонимный клиент без cookie). Проверки ролей пользователя досок, участника по ссылке и администратора появятся в T1.1–T3.1; здесь роли фиксируются только в части заголовков фрейма, одинаковых для страниц всех ролей (`/login`, `/`, `/admin/login`, `/admin/users`, `/b/{token}`).

## Сценарии

| Проверка | Роль | Сценарий | Тип (авто / ручной) |
| --- | --- | --- | --- |
| ARCH-STACK-01 | — | Позитивный: `docker compose -p myboard-qa down -v && up --build` на пустых томах поднимает ровно четыре сервиса `caddy`, `web`, `api`, `postgres`, все в состоянии running (healthy, если есть healthcheck) | ручной (команда + `docker compose ps`) |
| ARCH-STACK-02 | — | Позитивный: в проекте Compose объявлены именованные тома для данных PostgreSQL и для `MEDIA_ROOT`; `MEDIA_ROOT` смонтирован в `api` | ручной (`docker compose config`, `docker volume ls`) |
| ARCH-STACK-03 | — | Граничный: после `down -v` тома удалены и повторный `up` стартует на пустых томах без ошибок (повторяемость запуска с нуля) | ручной |
| ARCH-STACK-04 | — | Позитивный: `.env.example` содержит все обязательные переменные `PUBLIC_BASE_URL`, `SECRET_KEY`, `DATABASE_URL`, `MEDIA_ROOT`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `MAX_UPLOAD_BYTES`, а также `HTTP_PORT`; пример `PUBLIC_BASE_URL` — `http://<IP в LAN>`, не `localhost` | ручной (чтение файла) |
| ARCH-NET-01 | посторонний | Позитивный: `GET {PUBLIC_BASE_URL}/` (IP машины в LAN, не `localhost`) отдаёт 200 и HTML собранной статики интерфейса | авто |
| ARCH-NET-02 | посторонний | Позитивный: Caddy публикует порт на `0.0.0.0` (не только 127.0.0.1) — `docker compose ps`/`port` показывает `0.0.0.0:80` | ручной |
| ARCH-NET-03 | — | Граничный: `HTTP_PORT` меняет опубликованный порт — стек QA на 80 и стек DEV на 8080 работают одновременно и не мешают друг другу | ручной |
| ARCH-NET-04 | посторонний | Позитивный: клиентский маршрут SPA (например, `/login`, `/boards/1`, `/b/<token>`) отдаёт HTML интерфейса (fallback на index.html), а не 404 Caddy | авто |
| ARCH-NET-05 | посторонний | Негативный: в отданной статике (HTML и JS-бандлы) нет строки `localhost`/`127.0.0.1` как адреса API или WebSocket | авто |
| ARCH-NET-06 | посторонний | Ручной: страница открывается по `PUBLIC_BASE_URL` в браузере (Claude in Chrome) без ошибок загрузки ресурсов | ручной |
| ARCH-PROXY-01 | посторонний | Позитивный: запрос под `/api/...` доходит до API, а не до статики — ответ не HTML интерфейса (JSON/ответ FastAPI, например 404 `{"detail":...}` или `/api/openapi.json`) | авто |
| ARCH-PROXY-02 | посторонний | Негативный: несуществующий путь `/api/<случайный>` отдаёт ответ API (не index.html SPA с кодом 200) | авто |
| ARCH-PROXY-03 | посторонний | Позитивный: WebSocket-рукопожатие на `ws://{host}/api/ws` доходит до API через Caddy: либо соединение открывается, либо сервер API отвечает на апгрейд (например, закрывает с кодом политики из-за отсутствия сессии), но не 404/502 от Caddy и не HTML статики | авто |
| ARCH-PROXY-04 | посторонний | Граничный: заголовки `Upgrade`/`Connection` проходят через прокси — ответ рукопожатия 101 или отказ, сформированный API (не 400 «Bad Request» прокси) | авто |
| ARCH-FRAME-01 | посторонний | Позитивный: `/` отдаёт запрет показа во фрейме — `X-Frame-Options: DENY`/`SAMEORIGIN` и/или `Content-Security-Policy` с `frame-ancestors 'none'`/`'self'` | авто |
| ARCH-FRAME-02 | пользователь досок, администратор (страницы их ролей, анонимно) | Позитивный: `/login`, `/boards/<id>`, `/templates`, `/t/<token>`, `/admin/login`, `/admin/users` отдают запрет фрейма | авто |
| ARCH-FRAME-03 | участник по ссылке | Позитивный: `/b/<token>` и `/b/<token>?object=<id>` (не embed) отдают запрет фрейма | авто |
| ARCH-FRAME-04 | внешняя страница | Позитивный: `/b/<token>/embed` не отдаёт запрета показа во фрейме: нет `X-Frame-Options`, а в CSP нет `frame-ancestors 'none'`/`'self'` | авто |
| ARCH-FRAME-05 | посторонний | Граничный: пути, похожие на embed, но им не являющиеся, запрет фрейма получают: `/b/<token>/embed/x`, `/b/embed`, `/boards/<id>/embed`, `/b/<token>/embedded`, `/x/b/<token>/embed` | авто |
| ARCH-FRAME-06 | посторонний | Позитивный: ответы API (`/api/...`) и статические ресурсы тоже отдают запрет фрейма («остальные страницы») | авто |
| ARCH-FRAME-07 | внешняя страница | Ручной/браузер: страница `/` во `<iframe>` чужого происхождения не отображается, `/b/<token>/embed` — отображается (загружается документ SPA) | авто (Playwright) |
| ARCH-FRAME-08 | посторонний | Граничный: заголовок запрета присутствует и на HEAD, и на ответе с query-строкой (`/?x=1`), и на пути с завершающим `/` (`/login/`) | авто |
