# T4.1 · QA-отчёт

Требования: COL-01, SHR-04 (канал WebSocket), SHR-06 (WebSocket, перенесено из T3.1); регрессия ACC-*, ADM-*, BRD-*, SHR-*
Коммит сценариев: <заполняется после коммита> (в `main` до чтения handoff)

Сценарии составлены только по `REQUIREMENTS.md` (COL-01, SHR-04, SHR-05, SHR-06), `ARCHITECTURE.md` (раздел 5 «Ссылка» — HTTP и WebSocket принимают cookie участника так же, как сессию владельца; раздел 6 — один документ Yjs на доску, структура `objects`/`trash`/`comments`/`timer`/`votes`/`notes`, сервер проверяет право, дописывает обновление в журнал и рассылает; «Журнал и снимки» — клиент при подключении присылает вектор версии, сервер отдаёт недостающие обновления; раздел 7 — `boards.updated_at` обновляется сервером при принятой правке, список «недавние»; раздел 10 — один WebSocket на открытую доску `/api/ws`, сообщение `sync` (вектор версии, обновление, полный снимок), сервер применяет `sync` к своей копии и только потом рассылает, повреждённое обновление закрывает это соединение, документ остальных не меняется, адрес WebSocket собирается из адреса страницы без `localhost`, после восстановления сокета клиент досылает накопленные правки) и блоку «Тестирование» T4.1 в `PLAN.md`, до чтения handoff и кода.

Роли:

- **владелец (пользователь досок A)** — открывает WebSocket своей доски, правит документ;
- **участник по ссылке** — с cookie этой доски открывает WebSocket и получает те же права на документ, что владелец (SHR-04, канал);
- **пользователь досок B** — без участия по ссылке не открывает WebSocket доски A;
- **администратор** — сессия панели не открывает WebSocket доски;
- **посторонний** — без cookie WebSocket не открывается;
- **участник с отозванной cookie** — после сброса ссылки не открывает WebSocket, а уже открытое соединение не продолжает получать и применять правки (SHR-06).

Границы толкования (фиксирую до чтения handoff):

- Протокол — клиент `yjs`, проверка через независимый WebSocket-клиент с `pycrdt`/`y-py`-совместимой библиотекой на стороне теста (публичный интерфейс — бинарные/JSON-сообщения `sync`; формат кадра берётся из handoff, но смысл — из ARCHITECTURE.md 10).
- COL-01 «без захвата объекта в единоличное редактирование»: два клиента одновременно (без ожидания ответа друг друга) меняют разные поля одного объекта в `objects` и вставляют текст в один и тот же `Y.Text` — после обмена оба документа побайтно сходятся (одинаковое состояние), обе правки присутствуют, ни одна правка не отклонена сервером, никакого сообщения о блокировке нет.
- «Текст одного объекта могут менять несколько человек сразу» — проверяется вставками в одну позицию и в разные позиции одного текста; результат — объединение обеих вставок, без потерь символов.
- Сервер «применяет к своей копии и только потом рассылает»: клиент, подключившийся после правок (поздний), получает текущее состояние, даже если все прежние клиенты уже отключились; после перезапуска соединения состояние то же (перезапуск контейнера `api` — проверка T4.3, здесь только как замечание).
- Повреждённое обновление (мусорные байты в `sync`, обрезанное обновление, неизвестный тип сообщения — последнее граничный случай): соединение отправителя закрывается; остальные соединения этой доски остаются открытыми и не получают ни мусора, ни изменения документа; новые правки после этого продолжают ходить; поздний клиент получает документ без следов мусора; сервер не падает (HTTP отвечает).
- Изоляция досок: правка доски X не приходит клиентам доски Y.
- `boards.updated_at`: принятая правка поднимает доску наверх в «недавних» (`/api/boards/recent` или эквивалент) у владельца; отклонённая (повреждённая) правка — не обязана; правка участником по ссылке тоже обновляет метку.
- Доступ к WebSocket: владелец и участник с действующей cookie — открывают; посторонний без cookie, пользователь B, администратор, cookie участника доски X на доске Y, несуществующая доска, удалённая доска — не открывают (отказ при рукопожатии или немедленное закрытие без данных документа). Отказ не раскрывает, существует ли доска (одинаков для несуществующей и чужой).
- SHR-06 (WebSocket): после сброса ссылки cookie, выданная по старой ссылке, WebSocket не открывает; уже открытое соединение участника по старой ссылке закрывается или как минимум не получает дальнейших правок и его правки не применяются (фиксация: требование «прежняя ссылка после сброса доску не открывает» + CLAUDE.md «сброс сразу отзывает старый токен и его сессии»); участник по новой ссылке открывает.
- Выход владельца / отзыв его сессии: WebSocket с отозванной сессией не открывается (граничный, регрессия ACC).
- Переподключение: клиент копит правки, пока сокет закрыт, и после переподключения они доезжают до второго клиента; правки второго клиента за это время доезжают до первого. Проверка — в браузере (провайдер `yjs` в `apps/web`), т. к. холста нет — через то, что доступно наружу (handoff); при невозможности — ручная проверка/замечание.
- Адрес WebSocket в клиенте строится из адреса страницы: в собранном JS нет `localhost`, браузер подключается к `ws://<PUBLIC_BASE_URL host>/api/ws`.
- Присутствие/awareness — не в этой задаче (T4.2); снимки — T4.3.
