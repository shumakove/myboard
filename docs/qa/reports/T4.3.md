Роли:

- **участник по ссылке** — те же права на холсте (SHR-04): его удаление тоже уходит в `trash`, в ленте — введённое им имя;

Способ наблюдения: только публичные интерфейсы стека — WebSocket `/api/ws` (независимый клиент `pycrdt`), HTTP, а для таблиц `board_updates`/`board_snapshots`/`board_events` — SQL-запросы только на чтение к сервису `postgres` стека `myboard-qa` (`docker compose exec postgres psql`), т. к. интерфейса истории до T8.2 нет. Код `apps/` не импортируется. Интервал снимков на стенде QA сокращается переменной окружения (значение — из `.env.example`/handoff), отдельно проверяется запуск без неё.

Границы толкования (фиксирую до чтения handoff):

- «Пока доска активна, раз в несколько минут — полный снимок»: после правок и истечения интервала у доски появляется строка `board_snapshots`; `state` — полное состояние документа (применённое к пустому `pycrdt.Doc` даёт то же содержимое, что у живых клиентов на момент снимка). Доска без правок новых снимков не плодит (повтор снимка без изменений — замечание, не баг: требование этого не запрещает).
- «Отрезает вошедшие в снимок обновления»: после снимка строки `board_updates` с `seq`, вошедшими в снимок, удалены; правки после снимка дописываются в журнал (порядок `seq` возрастает, не сбрасывается так, чтобы ломать порядок).
- «Снимки остаются, пока доска не удалена»: после второго интервала с правками первый снимок на месте, снимков ≥ 2, `created_at` возрастает.
- «Сервер отдаёт недостающие обновления либо один полный снимок»: поздний клиент с пустым вектором после сжатия получает полное и корректное состояние (все объекты, вложенный текст, `trash`); клиент с частичным вектором, снятым до сжатия, сходится к тому же состоянию; правки после снимка (хвост журнала) тоже приходят; удалённые ключи не «воскресают».
- Гонка: правки, идущие непрерывно во время снятия снимка, не теряются (поздний клиент после серии правок через границу интервала видит все).
- Перезапуск контейнера `api` (`docker compose restart api`, а также `stop`/`start`): содержимое доски сохраняется — и вошедшее в снимок, и правки из хвоста журнала, ещё не попавшие в снимок; после перезапуска новые правки ходят и снова сжимаются.
- Изоляция: снимок доски X не содержит объектов доски Y; сжатие журнала X не трогает журнал Y.
- ARCH-T42-02: после обмена `awareness` (курсор, имя) и снятия снимка `state` не содержит имён, курсоров, `presence`/`awareness`; верхний уровень снимка — только структуры документа (`objects`, `trash`, `comments`, `timer`, `votes`, `notes` или их подмножество).
- COL-08 (основа) «удаление объекта переносит его в `trash`»: после удаления объекта клиентом (способом, который описывает handoff для клиента `apps/web`; если сервер сам переносит при удалении ключа из `objects` — простым удалением ключа) у всех клиентов и у позднего клиента объекта нет в `objects`, а в `trash[id]` есть `{ object, deletedAt, deletedBy }`, где `object` — прежнее содержимое объекта. Запись в `trash` переживает сжатие журнала и перезапуск `api`.
- «Добавляет запись в ленту действий»: удаление порождает строку `board_events` этой доски: `actor_name` — имя из сессии (имя учётной записи владельца / введённое имя участника), а не значение, присланное клиентом (подменённый `deletedBy` в документе не меняет `actor_name`); тип действия — удаление; `payload` содержит id удалённого объекта (нескольких — при удалении нескольких за раз). Правки без удаления событий удаления не создают; удаление несуществующего объекта или повреждённое обновление события не создаёт. Событие удаления, сделанного по отозванной (после сброса ссылки) cookie, не появляется.
- Повреждённое обновление по-прежнему закрывает только отправителя и не попадает ни в журнал, ни в снимок (регрессия ARCH-T41/COL-01).
- Переменная интервала снимков необязательна: стек стартует без неё; её отсутствие не мешает запуску (обязательный список переменных CLAUDE.md не расширен).
- HTTP-маршрутов истории в задаче не ждём; если handoff их добавляет — доступ проверяется в ролях владелец / участник / B / администратор / посторонний.
